# Code review: Web Push уведомления

Ветка `backend/notifications`, коммит `9be03df` («Добавил уведомления»), поверх `main` (`db5e927`). Смотрел только бэкенд: доставка, настройки, подписки, воркер, миграция `0010`, контракт API и тесты. Фронт в ветке не менялся.

Вердикт: каркас рабочий и его можно мержить как первую версию, но два поведения теряют напоминание без повтора, а одно даёт серверу ходить по произвольному URL от имени пользователя. Ниже это пункты 1–3.

## Статус исправлений

Пункты 1–6 исправлены в рабочем дереве поверх `9be03df`, не закоммичено. 313 тестов, `ruff` чистый.

| Пункт | Что сделано |
|---|---|
| 1 | Воркер выбирает только пользователей с включённым Web Push и хотя бы одной подпиской. Без ключей VAPID запись не захватывается. При полном провале `delivered_at` сбрасывается (`release_delivery`), следующий проход повторяет, пока запись моложе `NOTIFICATIONS_MAX_LATENESS`. |
| 2 | Если доставлено хотя бы одно устройство — `ok=true`, при частичных ошибках `error=partial_failure`. |
| 3 | Только `https`, до 2048 символов, хост из `WEB_PUSH_ALLOWED_HOSTS` (FCM, Mozilla, Windows, Apple и их поддомены). Иначе `422` на поле `endpoint`. Отправитель такие подписки удаляет. |
| 4 | `WEB_PUSH_TIMEOUT`, по умолчанию 10 секунд, передаётся в `webpush_async`. |

## Что сделано хорошо

- Старый контракт тостов не сломан. `status` по-прежнему меняет только клиент, `GET /notifications?due=true` значит то же, что раньше. Внешняя отправка живёт в отдельном `deliveredAt`.
- Пути `settings`, `web-push/*` и `test` объявлены раньше `/{notification_id}`, поэтому не превращаются в id.
- Все новые ручки требуют авторизацию. Чужую подписку `DELETE` не удаляет и отвечает `204`. Повторный `POST` с тем же `endpoint` обновляет ключи и переносит подписку на текущего пользователя.
- Захват записи — условный `UPDATE ... WHERE delivered_at IS NULL` с немедленным `commit`. Два процесса не отправят одну запись дважды. Это покрыто тестом.
- Ответ push-службы `404` и `410` снимает подписку. Ошибка одной записи логируется и не останавливает цикл.
- Включение Web Push без ключей VAPID — `503 WEB_PUSH_NOT_CONFIGURED`. Приватный ключ в конфиге с `repr=False`.
- Слои соблюдены: домен и application не импортируют infra. Миграция `0010_notification_delivery` одна голова, FK с `ON DELETE CASCADE`, `endpoint` уникален, есть `downgrade`.
- Тесты выключают воркер через `NOTIFICATIONS_WORKER_ENABLED=false`, так что pytest не шлёт настоящие push.

## Замечания

### 1. Напоминание сжигается до успешной отправки

Серьёзность: высокая.

`DispatchDueNotifications.deliver` сначала вызывает `claim_delivery`, и только потом смотрит настройки и шлёт. `claim_delivery` сразу коммитит `delivered_at`. Если настроек нет, Web Push выключен, подписок нет или `send` бросил исключение, поле уже заполнено, и следующий проход эту запись не возьмёт.

```python
# backend/src/app/application/notifications/delivery.py
async def deliver(...):
    claimed = await self.notification_gateway.claim_delivery(...)  # commit сразу
    if settings is None:
        return []  # delivered_at уже записан
```

Практический случай: напоминание наступило в 10:00, пользователь включил пуши в 10:01. Воркер уже пометил запись доставленной и ничего не отправил. То же самое при сетевой ошибке push-службы: повтора нет, в логе одна строка.

`test_failed_subscription_does_not_block_the_other` это фиксирует: после ошибки `deliveredAt` не пустой, второй проход ничего не шлёт. Для защиты от дублей между процессами захват нужен, но при полном провале `delivered_at` стоит сбрасывать, а захватывать только когда канал включён и есть хотя бы одна подписка.

Документы расходятся с кодом. В `NotificationReadResponse` поле описано как «when an external channel accepted the reminder». В начале `docs/notifications.md` — «уже ушло в Web Push» и «пока поле пустое, цикл пытается отправить». В разделе про сервер честно написано, что метка ставится в момент захвата. Для фронта `deliveredAt` сейчас значит «цикл уже брал эту запись», а не «пуш доставлен».

### 2. Частичный успех выглядит как полный провал и тоже без повтора

Серьёзность: средняя.

Если из двух подписок одна ушла, а вторая упала, `_send_web_push` возвращает `ok=false, error=delivery_failed`, хотя первое устройство уведомление получило. `POST /notifications/test` покажет ошибку. Повторно вторая подписка ничего не получит: запись уже захвачена (пункт 1).

```python
# backend/src/app/application/notifications/delivery.py, _send_web_push
if failed:
    return ChannelDeliveryResult(channel=WEB_PUSH, ok=False, error="delivery_failed")
```

Имеет смысл вернуть успех, если доставлено хотя бы одно устройство, и отдельно перечислить неудачные endpoint. Повторять стоит только те, что не получили пуш.

### 3. Подписка — это произвольный URL, на который ходит сервер

Серьёзность: средняя.

`WebPushSubscriptionBody` принимает любой `http` или `https` URL. Воркер делает туда POST через `pywebpush` с ключом VAPID. Авторизованный пользователь может указать внутренний адрес (`http://127.0.0.1`, адрес соседнего контейнера, metadata endpoint) и заставить API сходить туда в момент напоминания или `POST /notifications/test`.

```python
# backend/src/app/presentation/http/schemas/notification.py
if parsed.scheme not in {"https", "http"} or not parsed.netloc:
    raise ValueError("endpoint must be an http(s) URL")
```

Для браузерного пуша достаточно `https` и хостов известных push-служб (FCM, Mozilla, Apple и их поддомены). `http` имеет смысл только для локальной отладки и в проде его лучше не принимать.

### 4. Один зависший endpoint останавливает рассылку и делит цикл с API

Серьёзность: средняя.

`PyWebPushSender.send` не передаёт `timeout` в `webpush_async`. В pywebpush 2.5 значение по умолчанию — `10000`, а `aiohttp` 3.14 читает его как секунды (`ClientTimeout(total=10000)`), то есть почти три часа. Воркер шлёт подписки по одной в том же event loop, что и FastAPI. Пока висит одна доставка, не уходят остальные напоминания и тормозит API.

В `sender.py` стоит задать свой таймаут на десятки секунд и не полагаться на дефолт библиотеки.

### 5. `Notification.type` больше ни на что не влияет

Серьёзность: низкая.

В API по-прежнему можно создать уведомление с `type=app`, `telegram` или `web_push`. Рассылка смотрит только `notification_settings.web_push_enabled`. Два источника правды: поле на записи и настройка пользователя. Клиент, который выставит `type=web_push` и будет ждать пуш, его не получит, пока пользователь не включит канал в настройках. Либо воркер должен уважать `type`, либо поле стоит перестать принимать в новых запросах и описать это в `docs/notifications.md`.

### 6. Мелочи контракта

Серьёзность: низкая.

- `expirationTime` в теле подписки принимается и выбрасывается. Протухшая подписка живёт до `404`/`410` от push-службы. Для браузерных подписок это обычно нормально, но в документации это стоит сказать одной фразой, а не только «не хранится».
- `p256dh` и `auth` в схеме не ограничены по длине, в таблице они `String(255)`. Слишком длинное значение даст `500`, а не `422`.
- `VAPID_SUBJECT` не проверяется. Спецификация ждёт `mailto:` или `https:`. Кривой subject всплывёт как `delivery_failed` в момент отправки, а не на старте.
- Число подписок на пользователя и частота `POST /notifications/test` не ограничены. Тестовая ручка шлёт настоящий пуш на каждое нажатие.
- `DELETE` с JSON-телом неудобен для части клиентов. Query-параметр `endpoint` уже есть, его и стоит считать основным.

### 7. Воркер обходит Unit of Work

Серьёзность: низкая, осознанный компромисс.

`claim_delivery` коммитит сессию сам, с комментарием про `synchronize_session=False`. Воркер после `deliver` откатывает сессию, если транзакция ещё открыта. Захват из-за отдельного коммита откат не снимает, так что дублей нет. Но шлюз, который коммитит сам, легко сломать следующим вызовом в той же сессии. Имеет смысл оставить это в коде как есть, пока захват и отправка не разведены по правилу из пункта 1.

## Чего нет в тестах

Покрыты настройки, `503` без VAPID, владение подпиской, одноразовая доставка, окно `MAX_LATENESS`, `410` и то, что `status` не меняется.

Нет тестов на:

- выключенный канал и отсутствующую строку настроек: сейчас оба пути ставят `deliveredAt` и ничего не шлют;
- полный провал отправки и ожидание повтора;
- ответ `POST /test` при частичном успехе;
- отказ схемы для `http://` и для не-push хоста, когда появится проверка из пункта 3;
- таймаут `webpush_async`, который реально уходит в aiohttp.
